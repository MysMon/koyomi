# PR タイトル・本文の書き方（内部開発者向け）

Pull Request のタイトルと本文の書き方を定める。コミットメッセージの規約は `CLAUDE.md` の開発ルール、利用者向け文書の文体は [docs-style.md](./docs-style.md) を参照。本文の構成は [`.github/pull_request_template.md`](../../.github/pull_request_template.md) に従う。

## 原則: 変更内容そのものを、自己完結で書く

PR の読者は 2 種類いる。いま差分をレビューする人と、将来 `git log` や blame からこの PR にたどり着く人。どちらも知りたいのは「この差分が何を・なぜ変えるのか」であって、この PR が生まれた経緯ではない。

コミット件名の「変更内容そのもの」原則と、利用者向け文書の「現在の仕様だけを書く」原則を、PR にもそのまま適用する。

**書かない**（PR の外の文脈に依存する情報）:

- 「◯◯の調査・監査・レビュー指摘で確定した項目を実装」 — 指摘元・経緯。読者はその調査を読めない
- 「タスク一覧のうち◯◯を除く全件」「◯件を対応」 — 内部のタスク管理の文脈。差分に存在しないものの列挙は情報にならない
- 「◯◯は見送り」「◯◯は別途」 — やらなかったことの列挙（例外は後述の「スコープ外」）
- 会話・チケット・社内資料を読まないと意味が取れない指示語（「前回の方針どおり」「例の件」）

**書く**（差分だけでは読み取れない情報）:

- **何を**: 挙動・API・構造がどう変わるか。ファイル一覧の再掲ではなく変化の要約
- **なぜ**: この変更が必要な理由。目的はライブラリ利用者・開発者にとっての価値で書く
- **なぜこのアプローチか**: 選択肢が複数あった場合は、採らなかった代替案と採った方式の欠点も短く書く（レビュアーが同じ検討を繰り返さなくて済む）
- **検証**: 実行した検証と結果。「テストが通る」ではなく何をどう確認したか。見た目に影響する変更はスクリーンショットか録画を添付する
- **レビュー観点**: 判断が分かれうる仕様決定・設計上のトレードオフ。レビュアーの注意を集中させたい差分と、レビューをどこから読み始めるべきか
- **破壊的変更**: 有無と移行手順

外部リンク（Issue・設計メモ・ベンチ結果）を貼るときは、リンク先を読まなくても要点が分かる文脈を本文に併記する。リンク先は将来消えたり読めなくなったりする前提で書く。

本文はレビュー終了まで実態と同期させる。レビューの往復で差分が大きく変わったら、マージ前に本文を現在の差分に合わせて書き直す。

## タイトル

コミット件名と同じ形式（`type: 説明`）で、PR 全体の変更内容を表す。複数の type にまたがる場合は主目的の type を選ぶ。件数・経緯・指摘元をタイトルに入れない。

## スコープ外の扱い

「やらなかったこと」は原則書かない。例外は、**差分を見たレビュアーが誤解しうる意図的な非対応**だけで、その場合は「スコープ外」ではなく仕様・理由として書く。

- 悪い例: 「React 18 対応は除外した」（タスク文脈の列挙。この PR の差分と無関係）
- よい例: 「`examples/` の依存バージョンは npm 公開後に更新が必要（現時点で未公開のため placeholder）」（差分内に存在し、レビュアーが指摘しうる箇所への説明）

## 関連 Issue・経緯の置き場所

- 対応する Issue があれば `Closes #N` で関連付ける。経緯は Issue 側に書けば PR 本文で繰り返さなくてよい
- 設計判断の背景で将来の開発者に必要なものは `docs/internal/` か実装コメントへ
- バージョン間の変更記録は `CHANGELOG.md` へ

## チェックリストを置かない理由

一般的なテンプレートにある著者チェックリスト（テスト追加済み・lint 通過済み等）は置かない。このリポジトリではそれらは `pnpm check` と CI が機械的に強制しており、手動チェックリストは形骸化して本文のノイズになるため。機械化できない確認事項が増えたら、チェックリストではなくまず機械チェック（`scripts/`）への追加を検討する。

## 参考

この規約は次の一次ソースの推奨を、このリポジトリのコミット・docs 規約と整合する形で取り込んだもの:

- Google Engineering Practices: Writing good CL descriptions（first line の書き方、アプローチの理由と欠点、リンクの文脈併記、レビュー後の説明更新）
- GitHub Docs: Creating a pull request template for your repository（`.github/pull_request_template.md` の配置仕様）
- Graphite / Awesome Code Reviews の PR 説明ガイド（レビュー開始点の明示、UI 変更のスクリーンショット、チケットリンクのみへの依存をアンチパターンとする点）
