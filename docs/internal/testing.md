# テスト規約（内部開発者向け）

Koyomi のテストの位置づけ・書き方・置き場所を定める。用語は [terminology.md](./terminology.md) に従う。

## テストの位置づけ

- **テストが仕様である。**「こうあるべき」という振る舞いの定義はテストで行い、テストが固定する。仕様を変えるときはテストを先に変える（TDD の Red はその宣言である）
- **docs/*.md は利用者向けの公開情報であり、テストとは別の成果物。**利用者に影響する振る舞いを確定・変更したときは docs にも反映し、テストが担保する挙動と矛盾させない（矛盾を見つけたら docs 側を直す）
- **テストから docs への参照・リンクは書かない。**テストの期待値はテスト自体で完結して読めること。自明でない期待値（DST 切替日の具体的な UTC 時刻、ISO 週番号の年跨ぎなど）には、値の**計算根拠**を短いコメントで添えてよい

## `.test.ts` と `.spec.ts` の使い分け

- **`.test.ts(x)`** — Vitest で実行する単体・結合テスト（jsdom 含む）。本リポジトリのテストは現在すべてこれに該当する
- **`.spec.ts(x)`** — 実ブラウザで実行する E2E・ビジュアル回帰などの**別レイヤーのテスト専用**に予約する（Playwright 等を導入した場合）。Vitest のテストに `.spec` を使わない
- つまり接尾辞は「テストの実行レイヤー」を表す。同じレイヤー内での目的の違い（振る舞いの確定か回帰防止か等）は接尾辞・ファイル分割で表現しない

## 置き場所と構造

- Vitest のテストは**実装ファイルと同階層の `*.test.ts(x)`**（1 実装ファイルにつき 1 テストファイル）。目的別の別ファイルや専用ディレクトリは作らない
- **describe はテスト対象の振る舞い・機能で分類する。**経緯・手法（「リグレッション」「監査で追加」等）によるグループ化はしない
- 複数モジュールにまたがる検証は、対象モジュールごとに分割してそれぞれのテストファイルへ置く

## 書き方

- **TDD 必須**（CLAUDE.md）: 実装より先に失敗するテストを書き、Red を確認してから実装する（Red → Green → Refactor）
- テスト名は日本語で「入力・条件 → 期待される振る舞い」が読み取れる文にする
- 実装詳細の意図的なピン留め（キャッシュの参照同一性・memo の再レンダー抑制・共有参照によるアロケーション回避など）は、それが性能・整合性のための固定であることがテスト名かコメントから分かるようにする

## 実行環境の前提

- テストプロセスは `TZ=Asia/Tokyo` 固定（`vitest.config.ts`）。他タイムゾーンの検証は `TZDate` や明示的な IANA ID 指定で行う
- DOM を伴うテストは jsdom。`getBoundingClientRect` / `elementsFromPoint` / `PointerEvent` など jsdom が実装しない API は既存テストのモックパターン（`mockRect` / `mockElementsFromPoint` / `MouseEvent` 代用）に倣う
- 単一ファイルの実行: `pnpm --filter @koyomi-cal/react exec vitest run <path>`。コミット前は必ず `pnpm check`

## カバレッジの考え方

- 境界条件を優先する: 範囲の両端（ちょうど / 1 つ超過）、排他端（`end`・`endTime`）、DST の切替日（存在しない時刻・二重に存在する時刻）、年末年始・うるう年、空配列・0 件・`undefined` と空配列の意味差、`editable: false`
- 省略可能なオプション・コールバックは「省略時に既定の挙動・DOM 出力が変わらないこと」を必ず対で検証する
- コールバックは「発火する条件」と「発火しない条件」（キャンセル・拒否・対象外ビュー）を対で検証する
