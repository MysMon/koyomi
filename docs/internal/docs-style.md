# 利用者向けドキュメントの文体規約（内部開発者向け）

利用者向けドキュメント（`docs/internal/` を除く `docs/*.md` と `README.md`）と、IDE に表示される公開 API の TSDoc の書き方を定める。用語の選定は [terminology.md](./terminology.md)、テストとの役割分担は [testing.md](./testing.md) を参照。

## 原則: 常に「現在の仕様」だけを書く

利用者向け文書の読者は「いま何ができて、どう振る舞うか」を知りたいのであって、ライブラリの開発経緯・互換性の判断・過去との差分には興味がない。

**書かない**（利用者にとって無意味な内部事情・経緯）:

- 「既存利用者の見た目・挙動を変えないための方針」 — 互換性判断の経緯
- 「従来どおり〜」「以前は〜」「〜されました」 — 過去のバージョンとの差分口調
- 「後方互換のため〜」 — 設計の言い訳
- 「今回の〜」「新ビュー・新機能」 — リリース単位の相対的な呼称（利用者には常に現在の機能一覧しかない）

**書く**（同じ情報の正しい表現）:

- 「省略時は〜です」「既定では〜です」 — 既定値と省略時の挙動
- 「有効にするには〜を渡します」 — opt-in の手順
- 機能名は正式名で列挙する（「年・複数月・リソース・タイムラインビュー」）

## 経緯・互換性情報の置き場所

- バージョン間の変更・追加・修正の記録 → `CHANGELOG.md`
- 設計判断の理由・実装の背景 → `docs/internal/` と実装コメント
- アクセシビリティ等で「なぜこの方式か」が利用者の実装判断に役立つ場合の設計根拠 → 利用者向け文書に書いてよい（例: `docs/accessibility.md` の ARIA パターン選定理由）

## 機械チェック

代表的な禁止表現は `pnpm terms`（`pnpm check` に含まれる）の `USER_DOCS_RULES` が利用者向けドキュメントに限って機械的に検出する（`scripts/check-terms.mjs`）。正当な例外は該当行に `koyomi-terms-ok` を付けて除外できるが、原則は書き換えで解消すること。機械チェックは代表パターンのみなので、これに通ることは文体規約への適合を保証しない — レビューではこの文書を基準に判断する。

公開 TSDoc は機械チェックの対象外だが、IDE のツールチップとして利用者の目に触れるため同じ原則で書く。
